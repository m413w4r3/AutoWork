# M1-A — External effects call-path map

Study point: `aa0cef3ee07525ca77d6b1358252ebf5735a3dde`. This is a source map of the current implementation, not an architecture decision. The ordinary operator tool registry and `BridgeInvestigator.turn` are separate paths.

## (a) Textual call graph

**Operator request and ordinary tools**

`POST /investigations/{id}/operator/tools/{tool_name}` → API request parsing and `Idempotency-Key` extraction → `OperatorToolInvocationService.invoke` canonicalizes legacy schema aliases, checks safe payload and idempotency, operator mode, disclosure permission and duplicate/recovery state → `InvestigationService.execute_tool_call` creates or loads `ToolInvocation`, reserves its persisted budget against the envelope, changes `PENDING → RUNNING`, and commits the unit of work → `RegistryToolDispatcher.dispatch` serializes within its in-process instance, checks registration/schema/policy/budget and calls its optional fresh-admission callback → registered adapter → provider port/HTTP transport → observation/archive and invocation/reservation completion, or `NEEDS_REVIEW` and later explicit reconciliation. Main references: `backend/src/cti_app/api/investigation.py:1461-1517`, `application/operator_tool_invocation.py:700-930,1031-1123`, `application/investigation_service.py:1007-1321`, `application/investigation_tools.py:619-798`.

* **VT reads:** registered `vt.*` tool → VT adapter normalizes selected fields → VirusTotal port/HTTP adapter (or configured proxy) → raw/summary observations. Classified `EXTERNAL_READ`; `vt.download_sample` is a separate `ACQUIRE` path. Registration: `application/investigation_vt_tools.py:1571-1705`; transport implementation: `infrastructure/virustotal.py:229-255,419-454`.
* **Shodan reads:** generated `shodan.*` tool → Shodan adapter checks capability and passed envelope → `ShodanHttpAdapter` passive host/search/domain/count endpoint → observations. Classified `EXTERNAL_READ`; registration and adapter: `application/investigation_shodan_tools.py:261-340,1175-1222`, `infrastructure/shodan.py:109-225`.
* **Retrohunt:** `retrohunt.submit` (`EXTERNAL_SUBMIT`) or status/results (`EXTERNAL_READ`) → adapter → `RetrohuntService`; submit validates provider/TLP/disclosure and prevalidated rule, persists a subject-scoped reservation/slot before provider submission; status/results retrieve provider data and record candidate observations. `application/investigation_retrohunt_tools.py:81-181`; `application/retrohunt.py:108-329`.
* **Acquisition:** `vt.download_sample` (`ACQUIRE`) → adapter → `HitAcquisitionService` rechecks current envelope and TLP/DNT, handles prior successful acquisition reuse, reserves acquisition budget → `VirusTotalSampleAcquisitionService` → VT file-download port → quarantined bytes/hash verification and evidence. `application/investigation_acquisition_tools.py:495-540,656-715`; `application/investigation_acquisition.py:191-450`; `application/sample_acquisition.py:282-447`.
* **Advisor:** `advisor.consult` is registered as `EXTERNAL_READ`, then its adapter prepares an editorial consultation and calls `submit_bridge_consultation_once`, which submits to the Bridge/model path; response is parsed as untrusted proposals and provenance is recorded. Thus the label is read-like although the implementation performs an external model submission. `application/investigation_advisor_tools.py:164-210,3328-3411,362-376,764-778,897-920`.

**Bridge-led investigator loop (separate from the tool registry)**

`InvestigationService.run` (Bridge-led mode only) → resolve/build or reuse context snapshot → check external disclosure and envelope → persist budget reservation and commit → `BridgeInvestigator.turn` → per-request callback rechecks current stop/envelope → `ModelConversationTurnTransport` / model gateway → provider adapter → persisted turn/model-run result → complete reservation and resume/stop. `run` returns immediately for `OPERATOR_LED`. References: `application/investigation_service.py:523-672,688-733`; `application/bridge_investigator.py:1172-1445`; `infrastructure` model conversation/model gateway path described below. This path has no `ToolDefinition.effect` classification.

## (d) Bypass, duplication, and coupling list

1. **No single mandatory dispatch interface owns external submission.** The intended operator route passes through the operator service and `execute_tool_call`, but `ToolAdapter.execute`, `RegistryToolDispatcher.dispatch`, provider ports and HTTP adapters are callable interfaces. Calling an adapter or transport directly bypasses the durable `ToolInvocation` and operator idempotency path. Registry dispatch still applies its own checks if called directly, but the pre-dispatch callback is optional (`investigation_tools.py:412-427`).
2. **Provider-specific direct paths have different gates.** Shodan's HTTP adapter is passive but does not itself know investigation G2 (`infrastructure/shodan.py:109-225`). VT transport methods similarly do not own the invocation journal or envelope admission (`infrastructure/virustotal.py:229 onward`). Direct `RetrohuntService.submit` retains its own durable policy/slot checks, but bypasses the generic invocation journal. Direct `HitAcquisitionService.acquire_hit` still has G2 gates; lower-level `VirusTotalSampleAcquisitionService.acquire` checks its passed capability/policy but does not itself enforce the full allowed-provider/acquire-flag admission done by HitAcquisitionService (`sample_acquisition.py:295-313,343-367`). The VT download port is a still lower seam.
3. **Advisor and main Bridge can enter model transport outside the ordinary registry.** Direct `InvestigationAdvisorTool.execute` has local passed-context disclosure checks but no central invocation record; `submit_bridge_consultation_once` receives an authorization boolean rather than loading the current envelope. Main `BridgeInvestigator.turn` accepts `external_llm_allowed` and optional `before_submission`; omitting the callback bypasses service's fresh-envelope check (`bridge_investigator.py:1172-1291`). `ModelConversationTurnTransport` / model gateway can also be called beneath the investigation service.
4. **Locks are local.** `_ACTIVE_OPERATOR_INVOCATIONS` serializes the same key in one process (`operator_tool_invocation.py:700-761`); dispatcher `_lock` serializes calls through one dispatcher instance (`investigation_tools.py:619-642`). Neither is a cross-process claim held through provider transport. Database invocation insertion has a unique operation key, and updates use version CAS, but that does not serialize the current policy decision with the provider request (`repositories/investigation.py:252-314`).
5. **Identity and normalization are coupled to layers.** Operator idempotency includes client key plus request payload digest; domain `tool_operation_key` identifies investigation/tool/schema/parameters and optional local cache identity, excluding purpose (`domain/investigation.py:400-427`). For the operator route the wrapper key is used, so there is no one persisted semantic identity for the normalized provider effect. The ephemeral semantic fingerprint covers selected advisor and VT fields, not all tool/provider params (`operator_tool_invocation.py:1330-1398`).
6. **The `normalized_parameters` field is not reliably transport-normalized.** `execute_tool_call` stores input `arguments` directly before the adapter (`investigation_service.py:1031-1038`). Dispatcher validates the JSON schema but does not replace the argument mapping with an adapter-normalized value. VT/Shodan/advisor/Retrohunt/acquisition implementations normalize later, locally at each adapter/service. Thus stored identity and replay data generally reflect client wire parameters, not the exact transport request.
7. **Classification boundary is porous by implementation.** `advisor.consult` is `EXTERNAL_READ` while it submits a model consultation. `EXTERNAL_ACTIVE` is treated as needs-review by generic dispatcher; provider submit tools use `EXTERNAL_SUBMIT`. Classification can change when registration code changes and can be replaced via registry methods; it is not a durable invocation field. No client-supplied effect label was found.
8. **Bridge retries/corrections have distinct request identities under one logical turn.** Confirmed pre-submission retry may use up to `MAX_PRE_SUBMISSION_ATTEMPTS=3`; invalid-output correction allows up to `MAX_CORRECTIVE_ATTEMPTS=2` beyond the initial submission. Attempt number changes Bridge idempotency keys (`bridge_investigator.py:59,1204-1210,1221-1354,1395-1445,1448-1462`). `InvestigationService` reserves one `BRIDGE_TURNS` unit per logical turn key (`investigation_service.py:636-659,3309-3313`), while callback rechecks envelope before each request. No Bridge provider pagination loop was found in `BridgeInvestigator.turn`; advisor editorial batching is a separate implementation (`investigation_advisor_tools.py:1203-1384`), and its normal execute path supplies `maximum_units=len(editorial_units)` (`245-261`), producing one chunk in that path.

**Identity and normalization detail.** The operator `operator:{key_digest}:{payload_digest}` binds a client idempotency key to exact request payload (arguments, schema version after legacy canonicalization, purpose and expected version); the API key is hashed rather than stored verbatim (`operator_tool_invocation.py:718-761`). `tool_operation_key` instead hashes investigation ID, tool name, schema version, and the supplied parameter mapping, with optional local cache identity; it excludes purpose (`domain/investigation.py:400-427`). Its `normalized_parameters` input is raw operator `arguments` in `execute_tool_call`, so this is not a canonical provider-effect identity. Bridge turn idempotency binds investigation, turn index, context SHA, prompt version and attempt (`bridge_investigator.py:1448-1462`); its budget operation key binds investigation, turn, context SHA and attempt (`investigation_service.py:3309-3313`). Retrohunt has a separate service operation key over source hash, corpus and parameters, with subject-scoped persisted slots (`application/retrohunt.py:108-182`).

**Normalizer by provider path.** VT tool adapters normalize fields such as file hashes, object IDs and dorks (`application/investigation_vt_tools.py:691-696,754,863-899,998,1186-1211,1732-1750,1790-1845`); Shodan tool validators and its HTTP adapter validate/normalize queries (`application/investigation_shodan_tools.py:665-683,767-792,929-945,1058-1082`; `infrastructure/shodan.py:133-220`); Retrohunt service normalizes hash/corpus/params (`application/retrohunt.py:129-150`); acquisition service normalizes requested hash (`application/sample_acquisition.py:295-313`); advisor trims question and parses evidence references (`application/investigation_advisor_tools.py:164-210`). These normalized forms are not written back into the durable `ToolInvocation` by the generic service.

## (e) Persisted states and races

| State/record | Persisted facts and transitions | Atomicity or race finding |
|---|---|---|
| `ToolInvocation` | `PENDING`, `RUNNING`, terminal statuses including `NEEDS_REVIEW`; stores operation key, tool/schema, `normalized_parameters`, purpose, reserved/consumed budget and response refs (`domain/investigation.py:18-27,430-525`). Unique DB operation key and version CAS (`repositories/investigation.py:159-314`). | Invocation update is a CAS, not a row lock. It is not checked atomically together with envelope/reservation immediately before transport. |
| Envelope and budget reservation | Envelope holds providers, TLP/disclosure flags and budget snapshot; reservation keyed by operation key/status. Envelope/budget repo `SELECT … FOR UPDATE` plus version CAS (`repositories/investigation.py:1414-1467,1517-1577`; models `models/investigation.py:547-665`). | Locks protect individual save transactions only. The service commits RUNNING plus reservation before dispatch (`investigation_service.py:1153`); no lock spans the later fresh check and network request. |
| Retrohunt submission slot | Subject/rule/corpus/parameters operation identity; `RESERVED`, `SUBMITTING`, completed or reconciliation-required state (`application/retrohunt.py:108-239`). | Slot is durable before submit; observed ambiguous/crash path does not automatically resubmit. This is an independent state machine beside `ToolInvocation`. |
| Acquisition attempt/artifact | Attempt and verified quarantine/sample metadata; successful same-hash result can be reused without another download; partial bytes/hash mismatch remain ambiguous (`application/sample_acquisition.py:282-447`; `application/investigation_acquisition.py:231-288,411-450`). | Lower acquisition attempt is independent from outer tool invocation. The outer observation wrapper adds invocation linkage; subject reuse is zero-download/zero-VT-unit on the reuse path. |
| Main Bridge request | Conversation turn and ModelRun carry request/idempotency identity, status, submission state/attempt and request id; model gateway locks/reconciles ModelRun (`infrastructure/database/models/model_execution.py:39-99`; `application/model_gateway.py:1125-1343`; `infrastructure/database/repositories/model_runs.py:24-40,146-220`). | These durable attempt checks prevent known ambiguous model submissions from being retried, but are not one transaction with investigation envelope/budget reservation. |

**Serialized decision point today:** there is a unit-of-work commit before provider entry that durably records an invocation/reservation, and individual PostgreSQL row locks/CAS protect envelope/budget/state saves. There is no PostgreSQL transaction or row lock that atomically claims the combined `{current envelope/admission, RESERVED budget, invocation RUNNING, Bridge attempt}` decision and holds that decision through dispatch. Invocation uses unique-key insert and version CAS; envelope/budget/state use row lock plus CAS.

**RUNNING → NEEDS_REVIEW race:** operator duplicate/replay handling can turn a persisted `RUNNING` invocation into `NEEDS_REVIEW` after reservation (`operator_tool_invocation.py:872-878`); service replay does the same (`investigation_service.py:1987-1990`). The original execution then invokes its fresh-admission callback, which checks envelope and reservation but not invocation status (`investigation_service.py:1190-1226`). If the reservation remains `RESERVED` and envelope scope still passes, source permits the original path to enter the adapter after the invocation was sealed for review. This is an inference from those checks and is a replay race across concurrent execution/recovery; a later invocation CAS may fail after the provider call.

**Ambiguous outcome and retry scope:** ordinary tool result handling treats errors without framework-attested pre-submission proof as uncertain, retains the reservation, and sets review rather than automatically dispatching again (`investigation_service.py:1250-1321,2761-2832`). Reconciliation accepts explicit `NOT_EXECUTED`, `EXECUTED_WITH_RESULT`, or `ABANDON` actions and records an analyst decision (`1784-1924`). Bridge confirmed pre-submission retry uses distinct attempts; unknown/post-submission result becomes `NEEDS_REVIEW`, not automatic resubmission (`bridge_investigator.py:1221-1394`). Corrective model requests can occur within the same logical turn and G2 envelope authorization; each call rechecks the callback, but one logical `BRIDGE_TURNS` reservation covers the bounded calls. No Bridge pagination request path was found.

**Reuse and lineage:** completed tool invocation replay returns stored response refs without redispatch (`investigation_service.py:1951-2035`). Registry `_completed` is only process memory (`investigation_tools.py:619-703`). Acquisition can reuse an already verified same-subject sample at no download cost and records reuse/acquisition evidence; outer result archival includes operation and invocation references (`investigation_acquisition.py:231-288,681-764`; `investigation_service.py:2037-2068`). Advisor observations retain Bridge invocation/idempotency, input refs and hashes, prompt/output provenance (`investigation_advisor_tools.py:897-920`). Retrohunt slot identity and candidate evidence link to submission/rule/corpus (`retrohunt.py:152-239,241-329`). A uniform cross-tool “reused result across different invocation keys” lineage/budget policy was not found; behavior is service-specific.

**Migration boundary:** no migration is implied by this map. Existing columns/constraints cover current statuses and identities. If implementation changes add persisted effect identity, normalized transport payload, new attempt/reservation states or cross-record uniqueness/claim fields, they would need additive schema migration(s) from current head. ADR-0007 freezes `0001_baseline`; subsequent migrations must be additive and validate the supported starting schema (`docs/adr/ADR-0007-frozen-baseline-and-c2-migration.md:19-45`). Existing status/column changes should not be described as additive without reviewing the concrete migration against current head.

## (g) VERIFIED / INFERENCE / UNKNOWN and open questions

**VERIFIED from source**

* Effect is attached to `ToolDefinition` in registration code and consumed by dispatcher/service. Operator input does not set it. Runtime registry methods can replace/remove registrations.
* Operator key and domain `tool_operation_key` are different identities. Persisted `normalized_parameters` receive raw `arguments`; adapter normalization is later and generally not persisted as one canonical request.
* Invocation/reservation are committed before operator dispatch; no transaction holds the admission decision through the external request.
* VT/Shodan/Retrohunt/acquisition/advisor classifications and main Bridge path are as tabulated above. Advisor external model submission is labeled `EXTERNAL_READ`.
* Generic external ambiguity, Retrohunt ambiguity, acquisition ambiguity and Bridge ambiguity have separate persistence/recovery implementations.
* Current Bridge code makes bounded pre-submission retries and corrective requests with distinct attempt identity; no Bridge pagination loop was located.
* ADR-0007 freezes baseline migration `0001` and requires additive future migrations.

**INFERENCE from current call paths**

* A replay/recovery worker that changes a tool invocation to `NEEDS_REVIEW` after reservation can race with the original execution and still permit its adapter call, because fresh callback checks envelope/reservation but not invocation status. No atomic transaction closes that gap.
* The operator key's inclusion of `expected_version` and `purpose` can make the same provider semantics a distinct client-operation identity; the ephemeral semantic guard only recognizes selected normalized fields.
* Direct adapter/transport entry is a policy bypass where that lower layer does not independently validate the full G2 context; several lower layers are intentionally service-facing, but Python visibility does not enforce that boundary.

**UNKNOWN / open questions**

* Which direct adapter/transport entry points are reachable from production composition or other internal callers beyond the inspected modules; the map establishes callable seams, not all runtime call sites.
* Whether any underlying HTTP SDK/proxy transparently retries VT, Shodan or Retrohunt requests, and whether provider-side idempotency exists beyond the explicit keys described here.
* Whether Bridge pagination is a planned/indirect provider feature outside `BridgeInvestigator.turn`; no pagination loop was found in the scoped Bridge implementation.
* Exact integration behavior under two independent application processes at the `RUNNING → NEEDS_REVIEW` boundary; this source audit did not run concurrency tests or PostgreSQL.
* Whether current migrations/schema validation need changes for a future design; that depends on the concrete persisted transition/identity proposal. No design is proposed here.

## Vocabulary used

The **module** and its **interface** determine the current **implementation** boundary; adapter and transport calls are the visible **seams**. In the ordinary path, registry dispatch has some **depth** in schema, policy and budget checks, while runtime **leverage** is limited by optional callbacks and callable lower-level adapters. **Locality** of the locks is process/dispatcher instance, whereas durable CAS/row locks are scoped to their individual database writes.
