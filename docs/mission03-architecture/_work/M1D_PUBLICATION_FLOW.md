**Scope:** Mission 03 Phase 1, Flux D, including the publication seam diagnosis; source-only review, not a full editorial or visual audit.  
**Code SHA:** `aa0cef3ee07525ca77d6b1358252ebf5735a3dde` (provided study SHA; worktree HEAD matched).  
**Labels:** VERIFIED means directly supported by current source/tests or the supplied Mission 02 audit; INFERENCE is an architectural conclusion; UNKNOWN is not established by available evidence.

## Flow

### Subject publication PDF

1. **Canonical article artifact.** The production artifact is selected by its exact artifact ID. `PublicationRenderService._prepare` requires stage `PUBLICATION`, status `VERIFIED`, and a canonical blob, reads and parses its JSON as V4/V5/V6, then hashes its canonical serialization. The artifact/blob and its immutable version own the canonical article content and source references (`publication_rendering.py:672`, `domain/publication_document.py:2525`). V4 remains readable; V5 carries the richer semantic/reference/IOC projections.

2. **Opinion augmentation is a new canonical artifact.** `AnalystPublicationService.publish_augmented_article` requires an approved opinion and its expected base SHA; it checks that the pinned base is a verified V5 publication for the same run/subject, verifies citations and TLP / `do_not_submit`, then delegates augmentation (`analyst_publication_service.py:55`). The augmentation creates a V6 wrapper containing the exact V5 base, opinion, rendered opinion section, and provenance (base artifact ID/SHA, investigation/opinion IDs and version, opinion SHA, reviewer and approver); it appends a new versioned publication artifact with augmentation metadata (`publication_augmentation.py:160`, `:380`).

3. **Selection and lineage.** For a V6 artifact, `_prepare` requires its `publication_augmentation` metadata and compares its base artifact ID, investigation ID, opinion ID/version and opinion-content SHA with V6 provenance; it assigns lineage `nature="augmented_publication"` and an approved opinion identity. A non-V6 artifact carrying augmentation metadata is rejected; a V6 artifact without pinned augmentation metadata is also rejected. Otherwise the nature is `base_publication`. The identity label and render-data lineage carry that distinction, artifact ID/version/SHA, opinion identity where applicable, renderer/version, template version/SHA, compiler/version and render time (`publication_rendering.py:768`, `:774`, `:809`; label helper `:94`; lineage helper `:126`). **VERIFIED:** render nature is selected from artifact metadata plus canonical schema/provenance, not inferred from a template label alone. **VERIFIED LIMIT:** `reviewer_id` and `approver_id` are stored in both V6 provenance and artifact metadata, but `_prepare` does not compare those copied fields; the generated opinion lineage also omits them. The canonical V6 document still owns those actor references.

4. **Projection to Typst input.** `TypstRenderer.render` accepts the canonical document plus a snapshotted template bundle, explicit identity label and optional target identities/media reference. It selects the fixed `RENDERER/publication.typ` entrypoint, projects content into deterministic render-data JSON, hashes both source and JSON, and returns media references and target-mapping data (`typst_rendering.py:801`). `project_publication_to_typst_model` unwraps V6 to its embedded V5 for article content, retaining V5 references, semantic spans, original indicators and IOC details; it adds opinion/detection/graph projections separately (`typst_rendering.py:971`). The Typst entrypoint loads `render-data.json`; helpers render the opinion section and the identity/provenance tail (`chpTypst/RENDERER/publication.typ:1`, `publication_helpers.typ:910`, `:1200`).

5. **Opinion display.** A V6 document requires an approved opinion and a matching rendered section. Domain validation checks the base-publication hash, opinion identity/version/content SHA, reviewer, protocol figures, and equality/order of rendered blocks, qualifications, certainty, refs and unresolved points (`publication_document.py:2008`). The projection uses `rendered_opinion` for V6 output; draft previews use draft opinion blocks and carry an unapproved watermark/header (`typst_rendering.py:280`, `:2269`, `:871`). **VERIFIED:** current V6 invariants prevent the final PDF projection from silently substituting draft opinion state or displaying rendered blocks that disagree with the approved opinion. `document_header` says “Avis — publication approuvée” for V6; separate `pdf_lineage.nature` identifies augmented vs base (`typst_rendering.py:871`; service checks above).

6. **Compiler execution.** The service loads and hashes the manifest-listed template files and a locked font snapshot. `TypstRenderExecutor` resolves each media reference, checks media kind and pinned figure metadata where present, creates a private workspace, materializes fonts and invokes the compiler (`typst_render_execution.py:112`, `:172`). `TypstSubprocessCompiler` verifies the Typst version, ignores system fonts, pins the creation timestamp, enforces time/output bounds, and checks that the result is a parseable, unencrypted PDF with at least one page (`infrastructure/typst_compiler.py:266`, `:389`). The application executor additionally checks PDF media type, header, byte count and SHA (`typst_render_execution.py:231`).

7. **PDF and render record.** `TypstRenderRunner.run` persists a source/input snapshot and render-data blob, writes PDF bytes to the artifact store, then marks the render succeeded with output blob ID, SHA and byte size in the repository. Failures are recorded with stable errors; acquisition/retry logic reuses or repairs a render by input hash (`typst_render_lifecycle.py:161`, `:182`, `:250`; `repositories/publication_render.py:191`). The input hash pins the publication artifact/content identity, renderer/version, template version/SHA, compiler/version, font bundle version, output format and render policy (`publication_rendering.py:739`). **VERIFIED:** the canonical artifact remains the owner of article evidence; the render row/blob store owns the generated PDF and render-input provenance. `render_draft_preview` instead compiles through the preview executor and returns bytes plus lineage without a persisted `PublicationRender`; `render_preview` uses the persisted lifecycle despite its name (`publication_rendering.py:293`, `:635`).

8. **Read and inspection.** `read_verified_render_pdf` returns bytes only when blob size and SHA match the render record (`typst_render_output.py:27`). The PDF inspection source repository resolves a PDF SHA to every matching succeeded publication or edition render, including source artifact/release identities; inspection also supports render-ID lookup (`repositories/pdf_inspection.py:26`, `:129`). The inspection service exposes integrity, page count/dimensions, parser warnings, fonts, word counts, occupancy and heuristic diagnostics; it can rasterize pages (`application/pdf_inspection.py:175`, `:638`). Edition preview PDFs are cached as preview provenance and do not become persisted render provenance (`pdf_inspection.py:150`; `edition_preview.py:406`). **VERIFIED:** inspection establishes byte integrity and structural/parser observations, not semantic completeness against the canonical document.

### Edition release PDF (sibling flow)

A frozen manifest supplies ordered, exact publication artifact references. `EditionPublicationService.assemble` checks manifest/release idempotency and edition version/state, builds an `EditionDocumentV2` from those pinned verified artifacts, stores canonical JSON and SHA, then appends an `EditionRelease` (`edition_publication.py:909`; `edition_document.py:57`). The document is renderer-independent and embeds parsed V4/V5/V6 publication documents in unique position order (`domain/edition_publication.py:469`). `EditionRenderService.render_pdf` verifies the stored edition-document SHA, loads the edition template/font snapshots, and pins the first successful PDF to the release (`edition_rendering.py:192`, `:354`). `EditionTypstRenderer` iterates the frozen publications through the shared publication projection and uses `RENDERER/edition.typ` (`edition_typst_rendering.py:79`; `chpTypst/RENDERER/edition.typ:1`). The disposable `EditionPreviewService` may build a partial composition preview and returns PDF bytes without creating release/render state (`edition_preview.py:273`, `:301`, `:406`).

## Completeness and provenance findings

- **VERIFIED — observable guarantees:** canonical schema parsing; exact artifact/version pins; V6 base/opinion consistency; ordered projection and deterministic JSON hashes; manifest/template/font identities; media checks; Typst version/PDF validation; persisted output blob ID/SHA/size; and PDF inspection by output hash. `font_bundle_version` is computed from the loaded bundle file bytes and is included in the render identity (`typst_compilation.py:77`, `:130`; `domain/publication_render.py:65`). Projection tests assert many mapped fields/sections and deterministic output.
- **INFERENCE — completeness limit in the scoped flow:** no general invariant comparing every canonical content element with final PDF text/visual structure was located. PDF parser success and nonzero page count do not prove that every timeline item, figure, table or opinion element appears. Focused projection and real-render tests cover selected content; they are not a universal completeness oracle.
- **VERIFIED — Mission 02 finding:** `docs/mission02/TYPST_REAL_PDF_AUDIT.md` records a nine-entry canonical chronology where a derived figure represented four exact-date entries and the template selected either figure or timeline, omitting five month/approximate-date entries. A narrow template correction renders unrepresented timeline entries beside the figure; current test `test_real_typst_chronology_keeps_month_only_events_beside_derived_figure` asserts a month-only sentinel. The Mission 02 record says the inspected real PDF predates this correction.
- **UNKNOWN — inspected real PDF completeness:** the supplied PDF’s canonical JSON was not an authorized input in Mission 02, so whether its source document omitted sections/assets or whether all expected source content was rendered remains unknown. The visual pages examined and clean parser output do not settle that question. The real PDF should not be treated as proof of the current chronology correction.
- **VERIFIED — provenance limit:** lineage records compiler name/version and an identity hash derived from those values, but `binary_sha256` is explicitly `null`; template SHA and font bundle content-derived version are recorded. This distinguishes a version pin from a digest of the actual compiler executable (`publication_rendering.py:613`, `:617`; `domain/publication_render.py:65`).

## Interface / seam assessment

| Seam | Assessment vs KEEP_EXISTING + narrow fixes | Evidence and rationale |
|---|---|---|
| `PublicationRenderService.render_pdf(artifact_id)` → persisted render | **KEEP** | Deep caller seam: one canonical artifact ID hides canonical validation, projection, media, template/font loading, compilation, retries/idempotency, persistence and provenance. Production callers need not assemble Typst internals. Keep focused renderer-contract tests below this seam. |
| `TypstRenderer.render(document, bundle, label, identities/media)` → `TypstRenderSource` | **NARROW_FIX** (keep the seam) | Small entrypoint hides the large projection implementation and is shared by publication and edition paths. Projection tests intentionally know render-data shape; this is useful contract coverage, though it couples them to the projection schema. Add/retain explicit canonical-to-render completeness checks for lossy/derived projections (the chronology regression is an example). No evidence supports replacing this module/interface. |
| `TypstRenderExecutor` / compiler port | **KEEP** | The executor owns workspace/font/media mechanics; the compiler port has fake and subprocess adapters. Tests can check media/workspace behavior and compiler behavior independently. This is a real seam with production and test doubles. |
| PDF inspection source/provenance seam | **KEEP** | Lookup by output SHA returns all persisted provenance matches, while preview cache provenance is separate. Inspection is appropriately a projection/diagnostic interface, not a canonical-content validator. |
| Edition release render | **KEEP** | Same lifecycle/executor and shared projection, with a distinct frozen-release selection contract. This review finds no renderer replacement need; defer editorial layout questions to their own review. |

**INFERENCE:** the production caller interface hides enough complexity. Renderer-focused tests do know Typst bundle/render-data internals, but they exercise that lower module’s projection contract rather than forcing ordinary publication callers through those details. The strongest narrow follow-up is a durable completeness oracle at the projection/render seam, with canonical expectation derived from a synthetic versioned document; this note does not design a replacement.

## Highest-risk findings for M5

1. **Completeness is the principal seam risk.** Hashes prove byte identity, and parser checks prove a readable PDF; neither proves a faithful mapping. Mission 02 provides a reproduced example and a focused regression test, but no universal check.
2. **Opinion display is guarded; copied actor metadata is a narrower provenance gap.** V6 requires an approved canonical opinion tied to an exact base, and the rendered section must equal its renderable opinion content. The render service reconciles core V6 identity fields with artifact augmentation metadata before assigning `augmented_publication`; reviewer/approver copies are not compared or emitted in PDF lineage.
3. **Current interface merits KEEP plus narrow fixes.** Preserve the single-ID service seam, projection contract tests, and persisted render/provenance lifecycle. M5 can decide whether the copied reviewer/approver fields need cross-checking and lineage exposure; no replacement design is indicated by this evidence.
4. **UNKNOWN remains for the inspected Mission 02 PDF:** its canonical document was unavailable, and the inspected output predates the chronology correction.
