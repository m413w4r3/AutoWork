## S2 escaped-JSON credential residual at this SHA

The current P10 gap is specifically in free-text assignment matching, not in structured mapping-key normalization:

- `_bounded_json` handles actual mappings key-by-key, then sends string values to `_redact_url` and `_redact_text` (`invariant_proposals.py:2209-2260`).
- `_TEXT_ASSIGNMENT` accepts straight optional quote characters around the label/delimiter/value, but its delimiter expects an optional literal quote followed by `:`/`=` (`:2301-2304`). In a textual escaped JSON serialization such as `{{\"auth\": \"VALUE\"}}`, the backslash before the closing quote after `auth` is not accepted; the assignment does not match and `_redact_text` returns the credential value unchanged (`:2350-2364`). This agrees with the S2 review’s current residual. Existing tests cover ordinary JSON text and ordinary quoted assignments but not escaped quotes (`backend/tests/test_invariant_proposals.py:1045-1070,1094-1122`).
- **Bounded `NARROW_FIX`:** extend only the assignment matcher to recognize a backslash-escaped quote around a known sensitive label and value; redact the value in place while preserving valid escaped delimiters and adjacent text. Add renderer-path cases for escaped double and single quote forms, and a benign neighboring value case. Do not parse/decode arbitrary serialization layers or add a decoder cascade.
- False-positive risk remains even with this narrow matcher: P10 `_sensitive_name` intentionally treats generic `auth`, `token`, `api_key`, `credential`, and `secret` names as credentials (`:2305-2335`). CTI evidence may contain attacker tokens, implant/config keys, malware `api_key` fields, or quoted credential-like strings as observations. Existing P10 tests assert redaction for generic `auth`/`token` labels (`backend/tests/test_invariant_proposals.py:1045-1091`), while Advisor tests explicitly preserve generic `api_key` evidence (`backend/tests/test_investigation_advisor_tools.py:2070-2140`). The P10 tradeoff needs a positive CTI-evidence oracle; broadening the regex alone must not broaden the label set.

## Advisor preparation timing and reparse

1. The dispatcher reserves the registered maximum (`BRIDGE_TURNS=1`, `CONTEXT_BYTES=max_input_bytes`, token estimate, and tool-seconds maximum) before it calls the adapter (`investigation_advisor_tools.py:3395-3405`; `investigation_tools.py:766-784`). `InvestigationService` persists the invocation and reservation before dispatch (`investigation_service.py:1031-1048,1110-1188`). The exact rendered prompt and final source set are not known at this point.
2. Inside `execute`, the adapter loads the snapshot, canonical evidence, restrictions and versioned source refs; redacts, selects the dossier, creates the manifest and transmitted refs, and renders the final prompt (`investigation_advisor_tools.py:323-435,436-550,624-723`; `advisor_dossier.py:304-933`). It then measures the final UTF-8 bytes and hashes those bytes (`investigation_advisor_tools.py:741-743`), archives the exact prompt before transport (`:744-763`), and submits that prompt and hash (`:764-778`). Thus source versions and final bytes/context hash are known **after reservation but before transport**. The transport idempotency key is bound to the final context hash (`bridge_investigator.py:264-268`).
3. Successful raw output is byte-hashed and archived separately (`investigation_advisor_tools.py:786-803`). The advisor-call observation stores input/output SHAs, source refs, prompt/dossier hashes, parser version and reparse context (`:900-1107`).
4. `ReparsePersistedAdvisorOutputTool` validates the original observation, output blob descriptor and bytes against the stored SHA, and checks the stored input refs (`investigation_advisor_tools.py:3432-3628`). It reuses the persisted `reparse_context` and requires its `transmitted_refs` to match; legacy reconstruction is only used when that context is absent (`:3587-3628,4188-4297`). It does **not** reload or reacquire canonical evidence and does **not** call Bridge. It runs the current typed parser and appends an idempotent reparse observation whose key includes parser version (`:3629-3637,3720-3770`).
5. Therefore a raw Bridge output **can be reinterpreted without a new consultation**, but the result is a separate recorded parser observation with raw output SHA, source refs and parser version. It is not automatically an opinion or canonical rule. A changed parser version permits a new append; old raw bytes and source observation remain addressable.

## Opinion versioning and provenance

- Opinion versions are immutable append operations guarded by expected version; a content SHA is computed from a canonical payload that includes opinion ID/version, source synthesis/base publication identities, blocks, refs, status and timestamps (`domain/analyst_opinion.py:553-626,739-776`; `analyst_opinion_service.py:378-480,481-555`). Compose binds current synthesis/base artifact identities and calls `_validate_bridge_provenance` before append (`:285-377,917-1028`).
- A Bridge-authored block must carry a draft reference whose `text_sha256` matches; an optional review reference must match the reviewed text hash (`domain/analyst_opinion.py:197-238,247-278`). The opinion service locates the persisted advisor-call observation, verifies its blob SHA/schema/invocation, then verifies output SHA, Bridge provenance, input refs and matching typed text/target (`analyst_opinion_service.py:917-1028,1029-1184`). Citation and policy checks run again at review/approval (`:829-916`).
- Preview pins exact current opinion version/SHA and current verified base publication/SHA, rechecks synthesis and citations, and returns a lineage manifest (`analyst_opinion_preview.py:81-180,250-302`). One provenance question remains: the API accepts a temporary `protocol_model_blob_id`, compiles figures, passes them to preview, and the preview renders a `replace(opinion, protocol_figures=..., content_sha256="")` while its returned opinion identity still reports the stored opinion SHA (`api/analyst_opinion.py:511-537`; `analyst_opinion_preview.py:181-187,278-301`). The render-data SHA fingerprints the actual preview, but the lineage does not visibly identify that temporary source blob. Whether this is an intentional unversioned preview variant or a pinning gap needs an explicit oracle.

## Missing oracles

- **Missing:** escaped-quote P10 input through `_normalize_context` → `_render_p10_prompt`; current tests cover plain JSON quotes but not backslash-escaped serialized JSON.
- **Missing:** P10 preservation of permitted CTI values whose field names are `api_key`, `auth`, `token`, `credential` or `secret`, alongside positive operational-credential redaction. Without this, reducing false positives could reintroduce operational leaks, and keeping broad redaction can erase evidence.
- **Missing:** the known signed-URL variants at the Advisor payload→fake-transport seam, including scheme-less and nonstandard parameter/fragment forms; current source proves only the listed matcher forms.
- **Missing:** all producer shapes for sample-derived evidence and linked summaries under all sample flags, especially any source that does not encode the sample SHA in `object_id`/refs. Existing test source covers several named shapes but does not prove every producer.
- **Missing:** historical advisor response corpus that exercises legacy v2, typed v3, parser-version reparse, reference ambiguity and the opinion authorship gate together.
- **Missing:** preview lineage oracle for a temporary protocol model: verify that the requested source blob and resulting figure identities are represented alongside the stored opinion pin.
