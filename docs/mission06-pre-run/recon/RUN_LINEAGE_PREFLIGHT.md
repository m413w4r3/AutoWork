## Q1 — verdict : `EXISTING_PATH`

Le chemin applicatif normal crée un `production_run` neuf pour le même sujet, puis lance la production ; il ne réinitialise pas les anciens runs. Il n’y a pas de lacune de code indispensable. La faisabilité **live** reste conditionnée à une édition non archivée, sans batch actif et sans run actif pour ce sujet.

- Lire d’abord `GET /api/subjects/{subject_id}` pour `edition_id`, `GET /api/editions/{edition_id}/production` pour batch/édition, puis `GET /api/subjects/{subject_id}/production/runs` pour l’historique. Routes : `api/subjects.py:61-68`, `api/production.py:2139-2153,3608-3627`.
- Création : `POST /api/editions/{edition_id}/production/batches`, corps `{"subject_ids":["d22822d4-27ce-47d2-9cc5-f84cf312986a"]}`, en-tête `Idempotency-Key` neuf. Le service capture un snapshot et ajoute run + éléments de batch en une transaction ; il refuse édition archivée, batch actif et run actif du sujet (`api/production.py:3570-3605`; `application/subject_production.py:804-887`). Le subject doit avoir une lignée de découverte admissible (`subject_production.py:303-337`).
- Le dispatch soumet le job initial `production.subject.sources` avec run/stage/génération et clé idempotente (`api/production.py:1282-1302`). Le worker enchaîne `SOURCES → REFERENCES → EXTRACTION → RELEVANCE_PROJECTION → SYNTHESIS → EDITORIAL_ENRICHMENT → ASSEMBLY` (`domain/production_pipeline.py:16-30`; `application/production_jobs.py:649-731`; `application/production_workflow.py:782-830`).

| SOURCES | Télécharge/archive les URL du snapshot ; pas de LLM. | `production_workflow.py:1025-1057` |

Les appels de production ci-dessus sont contrôlés par la divulgation/TLP des sources, pas par une enveloppe G2 d’investigation qui n’existe pas encore. Pour les appels VT/Bridge de la nouvelle investigation, appliquer ensuite l’enveloppe G2 ou la politique `OSINT_OPEN` épinglée ; cette dernière reste intersectée avec la divulgation du snapshot (`api/investigation.py:866-902`; `application/osint_open_policy.py:295-371`).

La réutilisation inter-run est content-addressée par `input_hash` : l’extraction tente le cache avant tout appel modèle (`production_workflow.py:1363-1402`). Un artefact exact doit être `VERIFIED` et son blob canonique lisible/intègre ; le service crée un nouvel artefact rattaché au run cible avec `reused_from_artifact_id`, conserve le blob canonique et le marque `VERIFIED` (`production_artifact_reuse.py:56-187`). La synthèse a la même réutilisation exacte par hash et valide sa lignée (`production_synthesis.py:3354-3368,3570-3632`). Donc pas de nouvel appel extraction/synthèse sur un hit exact ; un hash différent, une invalidation ou un candidat invalide peut provoquer un nouvel appel, sous les gardes de divulgation. C’est le chemin applicatif versionné, pas une copie SQL manuelle.

Une synthèse fraîche n’est `VERIFIED` qu’après parsing/validation stricte des propositions, preuve de l’exécution archivée et contrôles de lignée/extraction/évidence ; `store_synthesis_result` écrit le blob canonique et l’artefact `VERIFIED` (`production_synthesis.py:3989-4109`; `production_stages.py:526-647`). Le GET d’artefact calcule `canonical_sha256` sur les octets canoniques (`api/production.py:2900-2955`). Le démarrage d’investigation exige run/sujet/artefact liés, stage `synthesis`, état `VERIFIED`, puis SHA canonique identique (`api/investigation.py:923-966,2708-2721`). Le modèle rend `analyst_investigations.production_run_id` unique (`models/production.py:336-340`).

**Live UNKNOWN :** edition, batch/run actifs, lignée de découverte, jobs, candidat de réutilisation, disponibilité provider et SHA obtenu. La route `/production/restart-with-new-sources` est un flux de réparation après changement d’URL qui repointe un élément de batch (`api/production.py:1865-1958`) ; le batch normal ci-dessus est le chemin de création retenu.
